# システム信頼性再構築計画

本ドキュメントは改善作業を5つのフェーズに分割し、各フェーズで達成すべき目標、実装ステップ、検証要件、成果物を整理しています。依存関係を考慮しつつ順次、または条件が整ったフェーズを並行で進められるようにプランニングされています。

## 進捗状況（2025-10-08 時点）
- データ健全性チェック (`data_management/data_health_check.py`) とレジストリ更新を実装し、`daily_trading_automation.py` に組み込み済み。
- テストスイートを再構成し、`pytest` 全61件をパス。レガシーモジュールのファクトリ関数を補完済み。
- バックテストエンジン V2 (`production/backtest_engine_v2.py`) を新設し、スリッページ・取引コスト・ポートフォリオ会計・ベンチマーク比較を取り入れたシミュレーションを実装。

## フェーズ1 — データパイプラインの安定化

**目的**
- すべての下流処理に対して完全・最新・一貫性のある入力データを保証する。
- 必要なデータが欠如/陳腐化している場合には早期に検知して停止する。

**実装ステップ**
1. **外部市場データの再収集基盤整備**
   - `YahooMarketData` などの取得クラスを再実装し、USD/JPY、VIX、S&P500、TOPIX、日経225、金、原油、JGB10Y など主要指標を明示的なスキーマで収集。
   - 取得した生データを `data/external/raw/YYYY-MM-DD/` に保存し、10年分のローリング期間を維持する Parquet マージジョブを実装。
   - 取得タイムスタンプや提供元メタデータを Parquet フッターや付随する JSON で記録。
2. **バリデーション／モニタリング層の構築**
   - `data_management/data_health_check.py` を実装し、想定シンボルの有無、欠損率しきい値、営業日連続性、プライス健全性（負値なし・連続ギャップが2営業日超の場合は警告）などを自動検査。
   - `daily_trading_automation.py` にヘルスチェックを組み込み、異常検知時は即座に処理停止。
   - チェック結果を構造化ログ `data_monitoring/data_health_{date}.json` に出力。
3. **銘柄ユニバースの正規化**
   - Nikkei225構成銘柄の有効日を含む CSV を `config/universe/nikkei225_members.csv` として管理（採用・除外日も保持）。
   - 取得スクリプトを有効日情報に従わせ、欠損銘柄は警告ログで明示。
4. **スキーマ契約の整備**
   - 中間データ（`nikkei225_complete`、`enhanced_integrated`、特徴量セット等）ごとに `schema.yml`（Great Expectations など可）を定義。
   - 保存時にスキーマ検証を実行し、検証失敗時は前回の「正常データ」を上書きしないよう制御。
5. **鮮度ガードレール**
  - 各データセットについて `data_registry.json` に最終更新日を記録（`data_management/data_health_check.py --registry data/data_registry.json` を活用）。
  - 自動化処理内で `target_date` と `data_registry` を比較し、1営業日以上遅延している場合は推奨生成を拒否。

**検証**
- 過去少なくとも2か月分に対してヘルスチェックを実行し、重大度高の指摘は解消する。
- 外部データを意図的に破損させた状態でパイプラインを走らせ、正常に停止することを確認。

**成果物**
- 新しいデータ取得スクリプト、バリデーションユーティリティ、スキーマ定義、運用手順書。

## フェーズ2 — モデリングワークフローの再設計

**目的**
- データリークと銘柄間のcross contaminationを排除し、再現性ある性能指標を得る。
- 信頼できる確率キャリブレーションを実現する。

**実装ステップ**
1. **銘柄単位の特徴量生成**
   - `create_enhanced_features` を銘柄ごとの grouped apply 形式に改修し、forward-fill が銘柄を跨がないよう統制。
   - 中間特徴量テーブルを銘柄/日付ごとに保存し、最初の行がニュートラル値で初期化されていることをユニットテストで担保。
2. **サンプル整列の正規化**
   - `Code, Date` でソートしたインデックスに `X`・`y` を結び付け、スプリットが常に確定的な順序で処理されるようにする。
   - データセットのスナップショットとハッシュを保存して再現性を確保。
3. **堅牢な時系列評価**
   - 現行のウォークフォワードを、purged time-series CV やアンカリングした拡張ウインドウ分割（例: 12か月学習／1か月テスト）に置換。
   - 最終学習データとは切り離したバリデーションフォールドを用意し、foldごとの precision@k、リフト、ヒット率などを記録。
4. **キャリブレーションの再設計**
   - 最後の3か月など独立したキャリブレーション用ホールドアウトを確保し、そのデータのみでイソトニック回帰またはプラットスケーリングを学習。
   - 信頼度曲線やブライアスコアを計測し、確率が過信/過小になっていないか監視。
5. **モデルレジストリとバージョニング**
   - `models/registry.json` に model_id、学習期間、特徴量群、パラメータ、検証指標、キャリブレーション結果などを記録。
   - アーティファクト（モデル、スケーラ、特徴選択器、キャリブレーション済み関数）をセマンティックバージョン形式 `models/enhanced_close_v2/{model_id}/` に保存。
6. **ハイパーパラメータ探索の衛生管理**
   - Optuna 等を実行する際は cross-validation 内に限定し、トレーニングと検証の混在を禁止。
   - RNG seed とデータセット ID を必ずログ出力。

**検証**
- 特徴量リーク防止（銘柄ごとに状態が保持されているか）、データ分割の整合性、キャリブレーション分離をユニットテストで確認。
- 凍結済みデータセットを用いて別のアナリストが再計算し、±1e-4 以内でメトリクスが一致するか検証。

**成果物**
- 再設計されたモデリングコード、学習 CLI、データ前処理〜評価〜キャリブレーションまでのフロー説明書。

## フェーズ3 — バックテストエンジンの再構築

**目的**
- 現実的かつ監査可能な過去パフォーマンスを算出し、スリッページやコスト、ベンチマーク比較を取り込む。

**実装ステップ**
1. **コードマッピングの修正**
   - 推奨レポートで扱う銘柄コードを5桁形式に統一し、`code + '0'` のような変換を廃止。
   - データレイク、レポート、バックテストで共通のフォーマットを使用。
2. **取引シミュレーションの中核実装**
   - エントリーは翌営業日の寄り（または VWAP等）+設定スリッページで約定させる。
   - 日中高値/安値のチェック順序を現実に沿うよう整理（寄り→高値/安値→終値）。同じ日にストップ/リミットに触れた場合の優先順位も明示。
   - 取引コスト、ポジションサイズ、借株／信用など `production_config.yaml` のルールに合わせて実装。
3. **ポートフォリオ会計**
   - 現金残高、マージン、エクスポージャー、実現損益／含み損益を日次で管理。複数日に跨る保有や `max_positions` 制限にも対応。
4. **ベンチマーク・リスク指標算出**
   - 日経225 ETF 等との比較、CAGR、最大ドローダウン、Sharpe/Sortino、勝率、平均損益、回転率などを計測。
   - 日次エクイティカーブ、トレードブロッターを `results/backtest_v2/` に保存。
5. **シナリオ・感度分析**
   - スリッページや発注遅延（+1営業日エントリー）などを可変パラメータとして CLI オプション化し、結果インパクトをレポート。
6. **レポート連携**
   - `production/backtest_engine_v2.py` を用いてバックテストを実行（例: `python production/backtest_engine_v2.py --report-dir production_reports/2025-10 --price-file data/processed/nikkei225_complete_225stocks_20251006_234325.parquet --benchmark-code 99840`）。
   - バックテスト結果を Markdown/PDF にまとめ、エクイティカーブやドローダウン、月次リターンなどの可視化を添付。

**検証**
- ランダムに5件程度のトレードを目視監査し、価格推移と約定ロジックが一致しているか確認。
- ランダムシグナル投入で収益がほぼゼロに近づき、ベンチマークリターン投入で指数とほぼ同一になるか確認。

**成果物**
- 新しい `production_backtest_v2.py`、設定例、検証用ノートブック／プロット、レビュー用チェックリスト。

## フェーズ4 — 運用ガバナンスとテスト体制の強化

**目的**
- 本番運用に耐える信頼性・監視性・リリースプロセスを確立する。

**実装ステップ**
1. **動的市場カレンダー**
   - 2025年ハードコードを廃止し、`jpholiday` や JPX カレンダー API のようなライブラリを導入。手動で例外追加できる仕組みも用意。
   - 複数年の休日・週末をテストで検証。
2. **テストスイートの再整備**
   - 古いモジュール（`temp_delete_candidates` など）は削除または隔離。
   - データ取得、特徴量生成、モデル学習、バックテスト、レポート生成に対する単体テストを再構築。APIアクセスはフィクスチャ（`tests/data/`）でモック。
   - 依存ライブラリが未インストールの場合は optional import やモックで対応し、テストが即失敗しないよう調整。
3. **CI（継続的インテグレーション）の導入**
   - `Makefile` や `tox.ini` で lint（flake8/pylint）、型チェック（mypy）、フォーマッタ（Black/isort）、pytest を統合。
   - GitHub Actions などで PR 時に自動実行し、主要アーティファクト（モデル指標、バックテストサマリ）を保存。
4. **ランタイム監視とログ強化**
   - ログをJSON形式へ変換し、`logs/automation/{date}.json` にデータ読み込み状況・モデルID・推奨銘柄数などを記録。
   - データ欠損、推奨ゼロ件、ヒット率急変などに対してアラート（メール、Slack等）を送出。
5. **変更管理の整備**
   - 新モデルを本番に昇格させるまでの手順（ステージ→シャドー→本番）とロールバック手順をドキュメント化。
   - 新モデル有効化前に確認すべきチェックリストを用意し、承認プロセスを設定。

**検証**
- 新規環境で CI が成功することを確認。
- ステージング環境で `daily_trading_automation.py` をダミー環境変数で実行し、ログ／アラートが期待通りに動作するか確認。

**成果物**
- テストインフラ、CIスクリプト、運用手順書、アラート設定。

## フェーズ5 — エンドツーエンド再評価と認定

**目的**
- 運用再開前に、客観的なエビデンスを用いて最低限の信頼性基準を満たしていることを確認する。

**実装ステップ**
1. **シャドーデプロイ**
   - 実際の取引は行わず、フルパイプラインを最低30営業日連続で稼働させ、デイリーのヒット率・キャリブレーション・ポートフォリオ指標を蓄積。
2. **パフォーマンスレビュー**
   - シャドー期間の実績とバックテスト期待値を比較し、偏差が1σを超える場合は根本原因を調査。
   - キャリブレーション図、混同行列、リスク指標をまとめ、実績が基準に達しているか確認。
3. **独立監査**
   - 別担当者によるコードレビュー、データセットハッシュ確認、サンプル計算の突合せを実施し、署名入りチェックリストを残す。
4. **Go/No-Go判断基準**
   - 定量的条件（例: precision@top5 がベースライン以上、最大ドローダウンが許容範囲内、Brierスコアが設定値以下など）を設定し、満たさない場合は保留。
   - エビデンスをまとめた「Readiness Dossier」を作成し、データリンク、ノートブック、ログ、承認記録を付ける。
5. **本番切替計画**
   - 切替手順、初期監視体制、指標が悪化した場合の即時対応策を明文化。

**検証**
- シャドー運用期間中に重大警告が発生せず、主要指標が基準値内で推移する。
- Readiness Dossier を関係者がレビュー・承認。

**成果物**
- 最終評価レポート、関係者承認記録、本番移行チェックリスト。

## 付録 — 目安スケジュールとリソース

- **フェーズ1 & 2 (4〜6週間)**: データエンジニア + MLエンジニアが中心。リーク対策完了前に新モデルを公開しない。
- **フェーズ3 (3〜4週間)**: クオンツ開発者が取引ロジックを実装し、QA がトレード検証を担当。
- **フェーズ4 (2〜3週間)**: DevOps/テストエンジニアが CI、監視、ドキュメント整備を担当。
- **フェーズ5 (最低6週間)**: 運用担当がシャドー運用を回し、アナリストが評価。

各フェーズ完了時には、主要設計判断と残存リスクを整理したADR（Architecture Decision Record）を作成し、Jira/GitHub等で進捗管理することを推奨します。
