# マルチモデル予測システム設計・実装ロードマップ

## 1. 背景と目的
- 現行の終値→終値モデルは「上昇確率のみ」を算出し、しきい値を下回る場合に候補がゼロになる傾向がある。
- マルチモデル化により、上昇・下落・リスクを多面的に評価してポートフォリオ候補を絞り込み、Precision と実運用のヒット率を同時に高める。
- ゴール: 推奨精度 (precision) を 60% 以上で安定させつつ、リスクの高い銘柄を除外し、日次の推奨件数を確保する。

## 2. モデル構成案
- **上昇モデル (Long Signal)**
  - 既存の Close-to-Close Precision System をベースに、キャリブレーション設定を 30 営業日 / 3,000 件で運用。
- **下落モデル (Short Signal)**
  - ラベル: 翌営業日で `Close_{t+1} / Close_t <= 0.99` など下落率ベースで検討。
  - 既存特徴量の再利用のほか、下落特有の指標 (出来高急増、陰線連続など) を追加学習。
- **ボラティリティ / リスクモデル (任意だが推奨)**
  - 翌日の変動幅 (1day Volatility) を定量化し、ハイリスク銘柄を順位調整 or 除外する。
- **アンサンブル/統合ロジック**
  - `score_final = w1 * P(up) - w2 * P(down) - w3 * Risk` の線形結合 or ルールベースで採用。
  - 各モデルのキャリブレーション後確率を入力とし、2段階フィルタ (例: P(up) >= 0.44, P(down) <= 0.30, Risk <= 0.6) を設定。

## 3. データ・特徴量要件
- **データスコープ**: 現行と同じく 10 年分の株価・外部指標を利用。J-Quants / Yahoo API で補完。
- **下落ラベル作成**:
  - `down_target_return` 例: -1%, -1.5% の複数シナリオを検証。
  - Imbalance 対策として SMOTE/UnderSampling か focal loss を適宜適用。
- **追加特徴量**:
  - ローソク足パターン、ギャップ率、直近ボラティリティ (5, 10 日)、出来高倍率、業種別モメンタム。
  - リスクモデルには Historical Volatility、ATR、ベータ係数などを投入。

## 4. 推論フロー (推奨)
1. デイリーパイプラインでデータ統合 → 前処理。
2. 上昇モデルで `P_up` を推定 (現行の推奨候補生成ロジック)。
3. 下落モデルで `P_down` を推定。高確率で下落と判断した銘柄は除外 or スコア減点。
4. リスクモデル (任意) でボラティリティ指標 `Risk_score` を算出。
5. 統合ルールでスコアリング:
   - 例: `score = P_up - alpha * P_down - beta * Risk_score`。
   - まず `P_up >= threshold_up` を満たす銘柄を抽出 → `P_down <= threshold_down` を条件化 → 残りをスコア順で並べ替え。
6. TOP N (既定 5 件) を出力し、レポートに各モデルの確率と判定結果 (例: `(下落モデル: 12%)`) を表示。

## 5. 評価指標と検証プロセス
- **基本**: Precision / Recall / F1 / Hit-rate (+1%達成率) をウォークフォワードで計測。
- **追加**: 
  - Downside モデルの適合率 (下落検知成功率)。
  - 統合スコアによるリターンシミュレーション (buy-hold 1day)。
- **検証ステップ**:
  1. 各モデル単体のキャリブレーション (Platt/Isotonic) を実施。
  2. 統合ルールごとに閾値網を探索 (GridSearch で `threshold_up`, `threshold_down`, `alpha`, `beta` を最適化)。
  3. 過去 12 ヶ月のローリングで precision ≥ 60% を満たすか確認。

## 6. 実装ロードマップ

### フェーズ 0: 企画・要件整理 (1 週)
- 使用ユースケース/評価指標の確定 (Precision > 60%, 日次件数 ≥ 2 など)。
- データ要件調査 (下落ラベル作成に必要な日付レンジ、欠損チェック)。

### フェーズ 1: 下落モデル & リスクモデルの PoC (2〜3 週)
- データセットに下落ラベルを付与し、LightGBM/ロジスティックで初期モデルを構築。
- ボラティリティ等のリスク指標を生成し、キャリブレーション指標 (Brier/ECE) を取得。
- `tests/` にユニットテスト追加（ラベル生成・予測スクリプトの正常系）。

### フェーズ 2: 推論統合としきい値探索 (2 週)
- 推奨ロジックに Downside フィルタを組み込み、レポート出力に `P_down`, `Risk_score` を追記。
- GridSearch/Optuna で `(threshold_up, threshold_down, alpha, beta)` を探索。
- 統合結果のウォークフォワード検証 (少なくとも最新 12 ヶ月で Precision >= 60%)。

### フェーズ 3: パイプライン実装とモニタリング (1〜2 週)
- `daily_trading_automation.py` にマルチモデル推論手順を組み込み。
- `production_reports/` のテンプレート更新、閾値未達/下落リスクの注記を追加。
- メトリクスダッシュボード (命中率・推奨件数・下落モデルの警告件数) を整備。

### フェーズ 4: 実運用前検証 (1 週)
- 直近 1 ヶ月のデイリーレポートを再生成し、ヒット率・リターンをシミュレーション。
- 実運用の Safety Check: 下落モデルが高確率で除外した銘柄が実際に大きく下げたかなどをレビュー。
- 最終レビュー後、`latest_calibrated_model.joblib` 等のリリース手順を更新。

## 7. リスクとフォローアップ
- **過剰除外**: 下落モデルが保守的すぎると、そもそも推奨が出なくなる → 閾値調整やハイブリッドスコアで対応。
- **推論コスト**: モデルが増えることで日次実行時間が延びる → 並列化やキャッシュを検討。
- **評価ドリフト**: 市況変化で上下モデルの精度が急低下する可能性 → キャリブレーションの期間・サンプル閾値を定期的に再計測。

## 8. 並行開発ガイドライン（Codex 2 名体制）

### 体制
- **Codex-A（モデル担当）**
  - 下落モデル・リスクモデルの PoC、学習スクリプトの更新、キャリブレーション調整。
  - `systems/`, `analysis/`, `tests/` のうちモデリング寄りディレクトリを主担当。
- **Codex-B（統合・パイプライン担当）**
  - 推奨生成ロジック、レポート出力、`daily_trading_automation.py` への組み込み、設定ファイル整備。
  - `reports/`, `production/`, `config/`, `automation` 系を中心に対応。

### 並行開発ルール
1. **ブランチ分割**: それぞれ `feature/multi-model-upside-downside`、`feature/multi-model-integration` 等の個別ブランチで作業。共有ファイルの変更を要する場合は PR/Issue ベースで事前調整。
2. **ファイル境界**: モデル担当は学習スクリプトと評価ノートブックの更新を主に行い、統合担当は推論パイプラインと設定・レポートを優先。`config/close_model_params.json` など共通ファイルは PR 説明で変更内容と影響範囲を必ず明記。
3. **データアーティファクト管理**: キャリブレーション用モデル (`models/enhanced_close_v2/*`) や検証ログは日付＋担当者名で保存し、`docment/ユーザー情報/モデル開発/マルチモデル開発/` に進捗メモを残す。
4. **同期タイミング**: フェーズ毎に小刻みな同期（PoC完了 → 統合試験 → パイプライン完成）を設定し、Codex-A がダミー出力 or API を用意、Codex-B が取り込みテストを行う。
5. **レビュー & テスト**: それぞれの PR は相互レビューし、`pytest` と主要シナリオ実行（推奨生成・レポート出力）を必須チェックに含める。

---
このロードマップに沿って各フェーズの成果物を管理すれば、マルチモデル化による精度向上とリスク制御を両立させやすくなります。
