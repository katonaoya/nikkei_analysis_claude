# codex_docs 自動実行プロンプト

## 目的
- Codex を非対話モードで連続実行する際の行動規範を提供し、タスク進捗と要件が常に同期された状態で開発を継続する。
- 実装に入る前に状況・制約・成功基準を深く思考し、拙速な変更を避ける。
- 各ループで `prompt.md` と `task_progress/` 配下（`current.md` / `completed.md`）を参照し、判断理由を明示したまま開発を進行する。

## docment/codex_docs フォルダ構成
- `prompt.md` : このプロンプト。非対話ループが最初に読むべき指針。
- `task_progress.md` : 進行中/完了済みログのインデックス。記録ルールと2分割されたファイルの位置を示す。
- `task_progress/`
  - `current.md` : 進行中タスク専用ログ。着手中の作業を詳細に記載し、完了時に `completed.md`へ移動する。
  - `completed.md` : 完了したタスクの履歴。実装内容・コマンド/テスト・成果物・学び/フォローアップを網羅する。
- `planning/`
  - `README.md` : 計画ディレクトリの使い方とファイル間の連携ルール。
  - `roadmap.md` : フェーズ単位の方針と成功基準をまとめたロードマップ。
  - `milestones.md` : 直近のマイルストーンを定義し、完了条件・依存関係・期限を管理。
  - `backlog.md` : マイルストーンから分解したタスク候補。着手時は `task_progress/current.md` へ移す。
- `performance_history.md` : 精度検証の結果を時系列で記録。最高精度を更新した際は上書きせず行を追加し、条件・コマンド・実装バージョンを詳細に残す。
- `requirements_summary.md` : プロジェクト全体の性能・精度・実装方針・優先アクションの要件。すべての意思決定の根拠。
- `検索リクエスト.md` : Web検索で調べたい事項を箇条書きで記録する専用ファイル。検索ニーズが発生したらまずここへ追記し、解消したら備考を残す。
- `research_result/` : 参考仕様・調査結果。必要になったときのみ開き、通常フローでは参照不要。
  - `gpt_research.md` : GPT 系アプローチに関する調査メモ。
  - `jquants_plan_spec.md` : J-Quants 連携計画と仕様。
  - `yahoo_finance_api_spec.md` : Yahoo! Finance API の利用仕様。

## requirements_summary.md で定義された中核要件
- Precision 60%以上（目標70〜75%）で翌営業日終値+1%以上上昇を命中させる。推奨銘柄は毎日3〜5件を維持する。
- 過去10年以上・日経225全銘柄の実データ（55万件超）を用いた学習/検証、および30営業日分の時系列CVを複数閾値で実施する。
- Precision向上はデータ拡張・特徴量設計・モデル刷新・網羅的パラメータサーチで行い、単なる閾値強化での精度稼ぎは禁止。Top3を毎日出し切ることを制約に含める。
- 既存パイプラインの影響を最小化し、必要なら独立プロジェクトとして実験し有効な部分のみ統合する。
- 優先アクション：信頼性フェーズの次ステップ確定、および Kabutan/Yahoo!/高頻度データの商用ライセンス方針・取得ログ実装の推進。

## 非対話ループで徹底する手順
1. **情報読込** : ループ開始時に `task_progress/current.md`（必要に応じて `completed.md` も）・`planning/`（特に `roadmap.md`／`milestones.md`／`backlog.md`）・`requirements_summary.md`・`performance_history.md`（最新精度の確認）・`検索リクエスト.md` を読み、未完タスクや検索ニーズ、制約を再確認する。
2. **思考と計画** : `current.md` に実行タスクがある場合は優先度順に着手。未登録の場合は `planning/` を使って実装方針と細かなマイルストーン（目的・成果指標・予定コマンド/検証内容）を作成し、`backlog.md` → `current.md` の順でタスク化する。計画のみのループでも、作成したマイルストーン/タスクを具体的に記録する。
3. **情報補足** : 目的、依存関係、テスト方針、リスクを文章で整理してから実装を決める。`research_result/` は参照が必要になった場合のみ開けばよく、通常ループでは見なくてよい。
4. **実装** : レポジトリ規約（Python 3.9, Black, ログ絵文字等）に従い、必要なコード/ドキュメントを編集する。変更中は破壊的操作を避ける。
5. **検証** : 実行したコマンドやテスト結果を把握し、成功/失敗を記録する。性能検証を実施した場合は結果と条件を整理し、最高精度を更新したら `performance_history.md` に新行を追加する。実行できなかった場合は理由とリスクを明記する。
6. **進捗更新** : 作業後に `task_progress/current.md` を最新状態に更新し、完了した内容は `task_progress/completed.md` へ詳細報告（実装内容・実行コマンド/テスト・成果物・未解決事項・次アクション）として追記してから `current.md` の該当行を削除する。計画やマイルストーンを更新した場合は `planning/` 内の該当ファイル（`roadmap.md`/`milestones.md`/`backlog.md`）も即座に同期し、計画のみ立てたループでも `current.md` に具体的マイルストーンを残す。
7. **報告** : ループ終了時のレスポンスでは、変更内容、参照ファイル、実行テスト、今後の提案を短くまとめる。

## 品質・安全ガイド
- 秘密情報（`.env` 等）を露出させない。必要なら `.env.template` で疑似値を共有する。
- `data_exports/`・`production_reports/` など外部共有が想定される成果物は必ずマスキングする。
- NumPy/LightGBM 等の依存更新時は macOS Accelerate 互換性を再確認する。
- 新しい振る舞いを追加したら `tests/` 配下に対応テストを作成し、可能な限り `pytest` を実行する。
- 問題や制約（sandbox, 権限, データ不足）があれば即座に `task_progress/current.md` およびレスポンスで共有する。

このプロンプトを毎ループで読み直し、要件への整合と深い思考を確認してから作業を開始すること。
